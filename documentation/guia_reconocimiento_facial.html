Guía del proyecto

Esta guía explica, paso a paso y desde cero, cómo se estructura el flujo de prueba de vida y comparación facial de este proyecto. La aplicación usa Ionic/Angular para la interfaz, Capacitor para integrarse con Android y un plugin nativo propio para abrir AWS Amplify Face Liveness.

Alcance y estado: el repositorio contiene el código del cliente y las URLs de los servicios usados. Esta guía describe cómo comprobar la configuración de AWS; no afirma que se hayan creado o modificado recursos en una cuenta AWS. Antes de entregar, complete los datos de la carátula, verifique las Lambdas y pruebe el flujo con una cuenta y un dispositivo autorizados.

1. Objetivo y conceptos básicos

El objetivo es obtener una sesión de prueba de vida, mostrar al usuario el detector facial de Amplify, recuperar la imagen de referencia que produce la prueba y compararla con la foto del perfil del usuario de referencia id_user = 1. La comparación la realizan servicios backend existentes.

  • Aplicación híbrida: interfaz web Angular/Ionic ejecutada dentro de un contenedor Android.
  • Capacitor: puente entre TypeScript y las funciones nativas de Android.
  • Plugin: adaptador que expone la operación nativa Face Liveness a TypeScript.
  • Prueba de vida: comprueba que la cámara está viendo a una persona en vivo; no compara por sí sola con la foto del perfil.
  • Comparación facial: una Lambda recibe las dos imágenes y responde si coinciden y con qué similitud.

Esta pantalla no convierte la prueba facial en el login del formulario. El formulario tradicional y el botón de verificación facial son flujos separados.

¿Por qué esta aplicación es híbrida?

La interfaz y parte de la lógica se escriben con tecnologías web: HTML, estilos y TypeScript con Angular e Ionic. En Android, esa interfaz se muestra en un componente llamado WebView dentro de una aplicación nativa. Capacitor conecta ambos mundos mediante un puente: permite que el código web invoque funciones implementadas en Android y reciba sus resultados. Por eso se considera híbrida: combina una interfaz web con un contenedor y capacidades nativas.

En este proyecto, el plugin propio FaceLiveness es una pieza de ese puente. TypeScript llama al plugin y este abre la pantalla nativa de Amplify. Capacitor integra la aplicación con Android; el plugin aporta una función específica, no genera el APK por sí mismo.

2. Arquitectura y flujo completo

  1. El usuario toca Verificar con rostro en la página Inicio.
  2. Angular llama a la Lambda 1 con GET y recibe un sessionId.
  3. El servicio TypeScript invoca FaceLiveness.startLiveness.
  4. Capacitor entrega esa llamada al plugin Kotlin registrado en Android.
  5. El plugin abre LivenessActivity; Android solicita permiso de cámara si hace falta y Amplify presenta el detector.
  6. Al terminar la prueba, Android devuelve éxito, cancelación o error al plugin y este responde a TypeScript.
  7. Si la prueba terminó correctamente, Angular envía el sessionId a la Lambda 2 y obtiene referenceImageBase64.
  8. Angular consulta el perfil /api/users/1/profile y obtiene fotoBase64.
  9. Angular envía las dos imágenes a la Lambda 3.
  10. La respuesta isMatch y similarity se convierte en un mensaje visible en la página.
InicioPage (Ionic)
  -> VerificacionFacialService.verificar()
  -> Lambda 1: crear/obtener sessionId
  -> FaceLiveness (TypeScript)
  -> Capacitor Bridge
  -> FaceLivenessPlugin.kt
  -> LivenessActivity + Amplify Face Liveness
  <- resultado de la actividad nativa
  -> Lambda 2: obtener referenceImageBase64
  -> API de perfil: obtener fotoBase64
  -> Lambda 3: comparar las dos imágenes
  <- isMatch / similarity
  -> mensaje en la página

2.2 Antes de abrir la aplicación: preparación de los dos mundos

  1. angular.json indica que el resultado de la compilación web se genera en www/. Esos archivos contienen la aplicación que se ejecutará dentro del WebView.
  2. capacitor.config.ts declara webDir: 'www'. Al ejecutar npx cap sync android, Capacitor utiliza esa salida para sincronizar la parte web con el proyecto Android.
  3. android/app/build.gradle incluye las librerías nativas de Capacitor y Amplify. Gradle genera el APK a partir del proyecto Android y sus recursos.

Este es el momento de empaquetado, no una llamada del botón facial. La naturaleza híbrida aparece al ejecutar la aplicación: Android abre un contenedor nativo que muestra una interfaz web; después, cuando se necesita la función facial, ambos lados se comunican mediante el puente de Capacitor.

2.3 Al tocar el ícono: Android arranca primero

En una instalación Android normal, el sistema operativo consulta android/app/src/main/AndroidManifest.xml. El filtro MAIN y LAUNCHER identifica MainActivity como punto de entrada. Este fragmento es del manifiesto:

        <category android:name="android.intent.category.LAUNCHER" />

Se muestran solo los atributos relevantes del manifiesto. Android crea esa actividad y ejecuta onCreate de android/app/src/main/java/io/ionic/starter/MainActivity.java: 

public class MainActivity extends BridgeActivity {
    @Override
    public void onCreate(Bundle savedInstanceState) {
        registerPlugin(FaceLivenessPlugin.class);
        super.onCreate(savedInstanceState);
    }
}
  1. registerPlugin(FaceLivenessPlugin.class) registra la clase nativa con Capacitor antes de iniciar la actividad base.
  2. super.onCreate(...) continúa el arranque de BridgeActivity, que proporciona el entorno de Capacitor y el WebView para la interfaz web.
  3. El WebView carga los archivos web sincronizados; por eso la pantalla Ionic se ejecuta dentro de la aplicación Android, no como una pantalla nativa escrita íntegramente en Kotlin.

El registro prepara el plugin para que pueda ser invocado; no significa que ya se haya presionado el botón ni que la prueba facial se haya realizado. El plugin también configura Amplify en su método load() cuando Capacitor lo carga. Una excepción al configurar se registra en el log.

2.4 Después: arranca Angular dentro del WebView

  1. La página base src/index.html contiene <app-root></app-root>, el lugar donde Angular inserta su componente raíz. Al compilar, Angular genera los archivos que el WebView cargará.
  2. El punto de entrada web src/main.ts ejecuta bootstrapApplication(AppComponent, ...). Entre sus proveedores configura Ionic, provideHttpClient() y el enrutador con routes.

  -> app.routes.ts -> inicio.page.ts + inicio.page.html

EL USUARIO PRESIONA EL BOTÓN
  inicio.page.html -> InicioPage.verificarRostro()
  -> VerificacionFacialService.verificar()
  -> HTTP GET a Lambda 1 -> sessionId

CRUCE DE WEB A ANDROID
  servicio TypeScript -> face-liveness.ts -> puente Capacitor
  -> FaceLivenessPlugin.kt -> Intent -> LivenessActivity.kt
  -> FaceLivenessDetector de Amplify

REGRESO DE ANDROID A WEB
  LivenessActivity: setResult(...) + finish()
  -> FaceLivenessPlugin.onResultadoLiveness(...)
  -> call.resolve(...) o call.reject(...)

CONTINUACIÓN EN WEB

El plugin no envía la foto a Angular en su resultado: devuelve que la actividad terminó o informa un error. La imagen se obtiene después, desde la Lambda 2. Tampoco es el plugin quien compara rostros: la comparación se solicita por HTTP a la Lambda 3 desde el servicio TypeScript.

6. Plugin nativo de Face Liveness

6.1 Android: permiso, pantalla y registro

El manifiesto declara Internet y cámara, y registra LivenessActivity. Android solicita el permiso de cámara en tiempo de ejecución antes de mostrar el detector.

En android/app/build.gradle se encuentran estas dependencias:

implementation project(':capacitor-android')
implementation "com.amplifyframework.ui:liveness:1.2.6"
implementation "com.amplifyframework:aws-auth-cognito:2.14.11"

La primera incorpora Capacitor para Android; la segunda proporciona el detector facial y la tercera integra la autenticación de Cognito con Amplify. En el plugin, load() inicializa Amplify al cargarlo: 

// FaceLivenessPlugin.kt: fragmento de load()
Amplify.addPlugin(AndroidLoggingPlugin(LogLevel.DEBUG))
Amplify.addPlugin(AWSCognitoAuthPlugin())
Amplify.configure(context.applicationContext)
amplifyListo = true

El código comprueba amplifyListo para evitar repetir la inicialización. Si esta falla, la excepción se registra con Log.e. La configuración utilizada está en android/app/src/main/res/raw/amplifyconfiguration.json.

La parte principal de FaceLivenessPlugin.kt declara el plugin y recibe la llamada:

@CapacitorPlugin(name = "FaceLiveness")
class FaceLivenessPlugin : Plugin() {
    @PluginMethod
    fun startLiveness(call: PluginCall) {
        val sessionId = call.getString("sessionId")
            ?: return call.reject("Falta sessionId")
        val region = call.getString("region", "us-east-2")
        val intent = Intent(context, LivenessActivity::class.java).apply {
            putExtra("sessionId", sessionId)
            putExtra("region", region)
        }
        startActivityForResult(call, intent, "onResultadoLiveness")
    }
}

@CapacitorPlugin asigna el nombre que TypeScript busca. @PluginMethod expone la función. El plugin pasa los parámetros de la sesión a una actividad Android, y luego resuelve o rechaza la llamada original.

El Intent es el mensaje de Android que abre otra actividad. putExtra adjunta sus parámetros. Con startActivityForResult el plugin indica que espera el resultado de LivenessActivity en el callback llamado onResultadoLiveness.

En LivenessActivity.kt, primero se revisa el permiso real de cámara. Declararlo en el manifiesto no sustituye la autorización del usuario: 

private val cameraLauncher = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { granted ->
    if (granted) mostrarDetector() else cerrarConError("Permiso de camara denegado")
}

override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    if (ContextCompat.checkSelfPermission(this, Manifest.permission.CAMERA)
        == PackageManager.PERMISSION_GRANTED) {
        mostrarDetector()
    } else {
        cameraLauncher.launch(Manifest.permission.CAMERA)
    }
}

Si ya existe el permiso, se llama inmediatamente a mostrarDetector(). De lo contrario, Android presenta la solicitud; el callback continúa solo si el usuario la acepta.

En LivenessActivity.kt, el detector recibe la sesión:

FaceLivenessDetector(
    sessionId = sessionId,
    region = region,
    onComplete = {
        setResult(Activity.RESULT_OK, Intent().putExtra("completed", true))
        finish()
    },
    onError = { error ->
        cerrarConError(error.message ?: "Fallo prueba de vida")
    }
)

onComplete finaliza la actividad con éxito. onError devuelve el problema al plugin. MainActivity.java registra la clase con registerPlugin(FaceLivenessPlugin.class); si no se registra, JavaScript no puede encontrar el plugin. El fragmento anterior omite el registro detallado del error para concentrarse en el resultado.

6.2 De Kotlin de regreso a TypeScript

Después de setResult(...) y finish(), Android devuelve el resultado a FaceLivenessPlugin.kt. El método indicado al abrir la actividad recibe el resultado: 

@ActivityCallback
private fun onResultadoLiveness(call: PluginCall?, result: ActivityResult) {
    if (call == null) return
    if (result.resultCode == Activity.RESULT_OK) {
        call.resolve(JSObject().put("completed", true))
    } else {
        val errorMsg = result.data?.getStringExtra("error") ?: "Cancelado"
        call.reject(errorMsg)
    }
}
  1. Con RESULT_OK, el plugin crea {"completed": true} y llama a call.resolve.
  2. Con cancelación o error, obtiene el mensaje enviado por la actividad y llama a call.reject.
  3. Capacitor transporta esa respuesta al WebView: la promesa que TypeScript esperaba se resuelve o se rechaza.
  4. Si la promesa se resuelve, continúa verificar(). Si se rechaza, el catch del servicio devuelve un mensaje y ya no solicita la comparación.

El objeto de éxito indica que la actividad terminó. No es el resultado de coincidencia ni contiene la foto: esos datos se solicitan después por HTTP.

6.3 TypeScript: interfaz del plugin y cruce del puente

El archivo src/app/services/face-liveness.ts describe el contrato JavaScript/Android:

import { registerPlugin } from '@capacitor/core';

export interface FaceLivenessPlugin {
  startLiveness(options: {
    sessionId: string;
    region?: string;
  }): Promise<{ completed: boolean }>;
}

export const FaceLiveness =
  registerPlugin<FaceLivenessPlugin>('FaceLiveness');

El nombre FaceLiveness debe coincidir con @CapacitorPlugin(name = "FaceLiveness") en Kotlin. La interfaz describe los parámetros y el resultado para TypeScript; no abre la cámara por sí misma. registerPlugin proporciona el objeto que el servicio usa para solicitar la función nativa.

El punto exacto en que la llamada sale del lado web es cuando verificacion-facial.service.ts ejecuta y espera FaceLiveness.startLiveness(...). Capacitor identifica el plugin FaceLiveness y el método startLiveness, y entrega la petición al método Kotlin registrado. El regreso ocurre en call.resolve o call.reject: Capacitor entrega el resultado a la promesa que el servicio está esperando.

7. Interfaz Angular y servicio de verificación

7.1 Botón y estado de la pantalla

En inicio.page.html, el botón llama a verificarRostro(). La página deshabilita el botón mientras se procesa la operación y muestra el mensaje final. 

<ion-button
  [disabled]="verificando()"
  (click)="verificarRostro()">
  {{ verificando() ? 'Verificando...' : 'Verificar con rostro' }}
</ion-button>

<ion-label *ngIf="mensajeFacial()">
  {{ mensajeFacial() }}
</ion-label>

El (click) de la plantilla ejecuta verificarRostro() en inicio.page.ts. La función activa el estado de espera, llama al servicio, guarda el mensaje y siempre restablece el botón al terminar. Este fragmento omite la línea de log y simplifica la anotación del error: 

async verificarRostro() {
  this.verificando.set(true);
  this.mensajeFacial.set('');
  try {
    const resultado = await this.verificacionFacial.verificar();
    this.mensajeFacial.set(resultado.mensaje);
  } catch (err) {
    this.mensajeFacial.set(`Error: ${err?.message ?? err}`);
  } finally {
    this.verificando.set(false);
  }
}

7.2 HttpClient y orden de las solicitudes

src/main.ts configura provideHttpClient(), lo que permite inyectar HttpClient en VerificacionFacialService. El método verificar() ejecuta las solicitudes en este orden:

  1. GET Lambda 1; extrae sessionId.
  2. Abre Face Liveness mediante el plugin nativo.
  3. POST Lambda 2; obtiene referenceImageBase64.
  4. GET del perfil; obtiene body.fotoBase64.
  5. POST Lambda 3; compara imágenes y muestra el resultado.

7.3 Paso a paso dentro de verificar()

Todos los fragmentos de esta sección provienen de src/app/services/verificacion-facial.service.ts; se omiten algunas líneas de log para concentrarse en el flujo. HttpClient devuelve observables y firstValueFrom permite esperar el resultado HTTP con await.

Paso 1: solicitar la sesión a Lambda 1.

const sesion = await firstValueFrom(
  this.http.get<any>(this.URL_GET_SESSION)
);
const sessionId =
  typeof sesion === 'string' ? sesion : sesion?.sessionId ?? null;
if (!sessionId) {
  return { acceso: false, mensaje: 'No se obtuvo sessionId' };
}

El servicio extrae el identificador de la respuesta y se detiene si no lo encuentra. HttpClient interpreta JSON por defecto; la rama que comprueba cadenas no configura por sí sola una respuesta HTTP de texto sin formato.

Paso 2: solicitar la prueba nativa mediante el plugin.

El servicio invoca FaceLiveness.startLiveness(...) con la sesión y espera la promesa. Mientras el usuario completa la prueba, la función queda esperando. Si el plugin rechaza la llamada, el catch retorna un resultado sin acceso y un mensaje de error. Los detalles de ida y vuelta están en las secciones 6.2 y 6.3.

Paso 3: pedir a Lambda 2 la imagen de la prueba.

const resultados = await firstValueFrom(
  this.http.post<any>(this.URL_GET_RESULTS, { sessionId })
);
const fotoEnVivo: string | null = resultados?.referenceImageBase64 ?? null;
if (!fotoEnVivo) {
  return { acceso: false, mensaje: 'No se obtuvo foto en vivo' };
}

La sesión identifica la prueba previamente completada. El servicio toma referenceImageBase64 como la imagen a comparar; si falta, termina con un mensaje y no llama a la Lambda de comparación.

Paso 4: consultar la foto registrada en el backend.

const perfil = await firstValueFrom(
  this.http.get<any>(
    `${this.URL_BACKEND}/api/users/${this.ID_USUARIO_REFERENCIA}/profile`
  )
);
const fotoPerfil: string | null =
  perfil?.body?.fotoBase64?.replace(/\s/g, '') ?? null;
if (!fotoPerfil) {
  return { acceso: false, mensaje: 'El usuario no tiene foto de perfil' };
}

ID_USUARIO_REFERENCIA vale 1. La app recibe la foto desde el backend, no accede directamente a la base de datos. El replace elimina espacios en blanco del valor Base64.

Paso 5: enviar las dos imágenes a Lambda 3 y preparar el mensaje.

const comparacion = await firstValueFrom(
  this.http.post<any>(this.URL_COMPARE, {
    sourceImageBase64: fotoEnVivo,
    targetImageBase64: fotoPerfil,
  })
);

return comparacion?.isMatch
  ? { acceso: true, mensaje: `Coincidencia: ${Number(comparacion.similarity).toFixed(1)}%` }
  : { acceso: false, mensaje: 'El rostro no coincide con la foto registrada' };

Si la Lambda informa coincidencia, se devuelve el porcentaje con un decimal. Si no, el servicio devuelve el mensaje de que los rostros no coinciden. El resultado vuelve a inicio.page.ts, que copia resultado.mensaje en mensajeFacial; la plantilla lo muestra al usuario. Los errores HTTP no capturados dentro del servicio llegan al catch de la página, que también muestra un mensaje.

La Lambda 2 usa referenceImageBase64 como imagen de la prueba. La Lambda 3 espera los nombres exactos sourceImageBase64 y targetImageBase64. La foto del perfil no debe ser nula y debe tener el formato Base64 que espera la Lambda.

El APK de depuración se genera en android/app/build/outputs/apk/debug/app-debug.apk. Para la entrega, use el nombre requerido por el curso, por ejemplo [nombre]_V1.apk.
